# 双电感舵机车：开源程序对照评估

评估日期：2026-10-21。范围：当前工程的双电感版本。四电感论文方案继续保留，本次只新增评估文档，没有修改固件源码、参数或 HEX。

后续实施记录（2026-10-22）：本次评估之后已按用户要求实现第 7 项“居中标定”、参考偏差补偿和运行前检查；下面 E 项保留为改动前的评估依据。当前使用方法见 README。

本报告依据已读取的公开源码和本地源码进行静态对照，没有对参考项目或本车进行实车验证。文中的归一化数值采用本工程 0～1000 标度；默认参数推导不代表当前 Flash 中实际保存的参数。

## 2. 当前程序的主要不足

### A. 优先处理：急弯与失线的区分

位置：`USER/src/track_core.c` 的 `TrackControl_Step()`；`USER/src/track_app.c` 的 `control_task()`。

当前逻辑主要由普通 PID、简单十字识别和失线保护构成，没有左急弯、右急弯和回线恢复状态。

举例：左归一化值 0、右归一化值 80，总和 80 小于默认失线阈值 150。核心层立即将 `signal_ok` 清零；应用层当帧就调用 `TrackHW_Stop()`，电机和舵机输出均关闭。核心层虽允许首个边缘弱信号帧暂不返回失线故障，但这不等于还在保持转向。因此，你提出的“右侧还有弱信号时继续右转，重新捕获后再恢复普通循迹”目前确实没有实现。

同类 GitHub 的 [pid.c](https://github.com/Alaye-Dong/ElectroSmartCar_quad/blob/c6ed4ac43c9b0e2c0815eff7adae4aa2ba1a6ff7/Project/MDK/pid.c#L156) 在普通循迹中包含单侧电感偏弱时给定较大固定转向的分支，说明特殊情况需要单独处理。但该分支也不是完整的峰值检测、方向保持和回线状态机，不能照搬后就认为解决了问题。

改进建议：增加“普通循迹→左/右急弯→回线恢复→普通循迹”的状态；进入条件参考连续帧、前一有效方向和信号强弱，退出条件参考存活侧变化趋势及另一侧持续恢复。两侧均失效、超时和硬件故障始终优先停车。

不要把“必须等右侧达到 1000 才退出”写成硬条件。实际急弯可能达不到标定最大值；可以记录局部峰值并结合另一侧恢复判断。具体阈值必须依据本车串口记录确定，不能只靠想象。

### B. 优先处理：默认 PID 与转向限位没有形成一致的转向能力

位置：`USER/src/track_core.c` 的默认参数及 PID 输出计算。

默认中值 750、左右限位 800/700，默认 Kp=40、Ki=0、Kd=0.15。当前 PID 内部输入为：

`e = (L - R) / (L + R)`，范围为 -1～1。

当偏差持续为 +1 或 -1，且微分项衰减后，比例项仅提供约 ±40 的占空比数值偏移，因此默认持续舵机命令约为 710～790，而非完整的 700～800。微分瞬态可以扩大转向，但不能提供持续的满幅转向。

这是默认参数下的结果；Flash 已保存的增益可能不同。仅把左右限位调得更宽，并不会自动让普通 PID 使用更大的转向量。

改进建议：先确认本车机械中值、实际轮角和安全限位，再把控制输出与可用转向幅度对应起来。急弯可使用独立的转向命令或分段增益，同时降速；不宜为了过急弯一味提高所有路况下的 Kp，否则直道可能摆动。还需实测最小转弯半径，超出机械能力的弯道无法仅靠增加 PID 参数解决。

### C. 优先处理：十字识别仍是简化启发式

位置：`USER/src/track_core.c` 的 crossing 分支。

当前依据左右都较强、偏差较小、总和相对前帧上升来触发十字状态，随后短时间将误差置零，最长 120 ms。其局限包括：

- 触发条件只要求一次明显上升，尚未验证普通直道幅度变化是否会误触发。
- 同样 120 ms 在不同车速下对应不同距离，不能保证刚好通过十字。
- 将误差设为零后，历史微分状态及非零 Ki 时的积分仍可能产生输出；“误差为零”不保证舵机立刻回到中值。
- 当前没有航向反馈，回中值也不等于保持实际航向。

参考 GitHub 的 [round.c](https://github.com/Alaye-Dong/ElectroSmartCar_quad/blob/c6ed4ac43c9b0e2c0815eff7adae4aa2ba1a6ff7/Project/MDK/round.c) 包含按编码器累计距离推进十字过程的做法；本车暂时没有编码器，不能照抄距离条件。

改进建议：以多帧证据确认进入，明确通过时的舵机命令和 PID 历史状态处理，结合信号形态退出，保留时间上限。现有硬件先验证低速通过效果；真正按距离或航向控制需要相应反馈。

### D. 重要：有按偏差降 PWM，但没有实际车速控制

位置：`USER/src/track_core.c` 的电机目标计算；`USER/inc/track_config.h` 的速度相关默认值。

当前根据瞬时偏差绝对值，在基础 PWM 与弯道 PWM 之间线性插值；加速有斜坡，降速直接生效。左右轮主要使用相同命令加固定补偿。没有编码器，所以这些数值代表电机占空比，不是实际车速。

不足是同一 PWM 的实际速度会受电池、摩擦、左右电机差异和负载影响；而且未结合急弯状态、误差变化速度、舵机是否接近限位来规划降速与出弯加速。速度相关参数也没有出现在现有六项菜单中。

GitHub 的 [pid.c](https://github.com/Alaye-Dong/ElectroSmartCar_quad/blob/c6ed4ac43c9b0e2c0815eff7adae4aa2ba1a6ff7/Project/MDK/pid.c) 和 Gitee 的 [motor.c](https://gitee.com/fantasy-q/19_-intelligent-car_-eleltronic-team/blob/master/19_IntelligentCar/Project/APP/motor.c) 都包含编码器反馈的速度控制。这是硬件条件带来的能力差别，当前仅增加一个“速度 PID”函数并不能获得闭环车速。

改进建议：现阶段增加可调基础 PWM、急弯 PWM 和出弯缓加速策略；后续有编码器再实现左右轮速度 PI。舵机车的轮速分配还应与机械转向关系一致，不直接套用差速车转向公式。

### E. 重要：极值归一化之后还缺少物理居中检查

位置：`USER/src/track_core.c` 的标定与归一化函数。

当前每路使用自己的最小、最大值：

`N = clamp((ADC - min) × 1000 / (max - min), 0, 1000)`。

这样可以统一量程并扣除本次标定得到的低端偏置，但不能保证车头实际居中时两路归一化结果相等。安装角度、高度、左右放大倍数以及两侧标定扫线是否充分都会影响结果。舵机机械中值校正与电感居中误差校正是两个不同问题。

改进建议：在完成极值标定后，将车摆正并检查左右信号及居中误差；必要时记录参考偏差或提示重新调整安装/标定，而不是只靠舵机中值掩盖电感不对称。新增参考值时也需验证左右急弯的误差范围与符号。

两路差比和还存在信息限制：L=0/R=200 与 L=0/R=1000 都给出 e=-1，方向误差本身无法区分存活侧强弱。因此状态识别仍需保留 L、R、总和和历史趋势，不能只看 PID 误差。

### F. 后续完善：滤波、标定质量和实际控制周期的测量

当前 ADC 已做切换通道后的首次转换丢弃，以及五次采样去掉最高最低后取均值，并非没有滤波。但标定的历史极值仍可能受偶发异常值影响；样本数量及跨度合格，也不证明左右扫线充分或工作时噪声足够低。

建议先记录电机关闭/开启时的原始信号、离线背景与居中信号，再决定是否加入轻量跨帧滤波、极值重复确认或信号有效性滞回。滤波太重会拖慢急弯响应，不宜直接堆长窗口平均。

当前前台按 5 ms 调度控制，PID 按固定 5 ms 计算；OLED 和串口格式化也在前台。已有超时停机保护，但仍缺少实际控制间隔、执行耗时与迟到次数记录。应先测量时间抖动，再决定调整任务负载或时间基准，不能仅凭配置值认定实际周期恒为 5 ms。

## 3. 现有实现应继续保留的部分

- 每次上电重新进行各通道独立标定，校验跨度、采样数量及高端饱和；重新标定失败不会覆盖原有效结果。
- PID 调参及舵机设置时电机禁止运行。
- 舵机软件限位、PID 输出限幅和积分抗饱和。
- 参数 Flash 双槽、CRC、最后提交标记和回读校验。
- ADC 等待有界、控制超时关输出、看门狗及串口队列。
- 已有归一化、控制、存储和应用/硬件接口测试。

这些机制解决了基础操作和故障处理问题，但现有测试通过并不代表实车已经验证过急弯、十字和不同电量下的表现。

四通道采集、标定和数据结构已有预留，而当前转向公式只用前两路。这属于明确保留的后续工作；将通道数设为 4 不等于已经实现论文中的四电感融合。

## 4. 开源代码也需要筛选

GitHub 项目的 [direction.c](https://github.com/Alaye-Dong/ElectroSmartCar_quad/blob/c6ed4ac43c9b0e2c0815eff7adae4aa2ba1a6ff7/Project/MDK/direction.c) 中存在五元素数组排序时可能访问第六项的越界问题。Gitee 的 [inductance.c](https://gitee.com/fantasy-q/19_-intelligent-car_-eleltronic-team/blob/master/19_IntelligentCar/Project/APP/inductance.c) 用 `sizeof(ADC)` 推导指针所指数组的长度，这也不成立。

因此应参考识别与控制思路，逐段审查后在本库接口上实现，不能整体移植。这些项目的电感阈值、PWM 值、舵机中值和增益也不具有跨车通用性。

## 5. 建议的推进顺序及验证方法

1. **先确定执行能力**：确认方向、中值、左右限位及最小转弯半径，核对默认/Flash PID 的持续输出是否足够。电机保持禁止，先完成舵机静态检查。
2. **补急弯与恢复状态**：用两路串口记录确定条件，验证弱单侧信号、左右镜像、噪声反复越阈值、信号恢复以及两侧失效。失线保护仍具有最高优先级。
3. **完善十字通过**：检查直道误触发、斜着进入、不同低速通过，以及十字过程中真实失线的处理。
4. **完善 PWM 规划及参数入口**：急弯提前降速、恢复后延迟加速，允许现场调整基础/弯道 PWM；测试满电和较低电量时的差异。
5. **增加测量数据**：在已有串口数据上增加状态、信号总和、状态进入/退出原因及控制周期统计，依据记录改阈值与滤波。
6. **再扩展硬件与四电感**：根据实际安装位置实施论文融合；有编码器再加入速度闭环，有 IMU 再评估航向辅助。

目前最应优先补齐的是急弯/恢复策略与转向能力匹配。继续增加普通 PID 参数，无法替代这两项工作。
